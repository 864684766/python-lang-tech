# 调试与答疑指南：从运行现象学到具体知识

阅读顺序：先看一段代码会接收什么、返回什么，再追踪谁保存状态、谁执行动作。一个案例只回答一个问题，遇到语法障碍时先用最小表达式验证，不必同时理解整个 Agent。

## 1. 每课都做一次“预测—暂停—核对”

例如调试 `hs_14_two_axes.py`，先问：模型这次是在写规则，还是按规则执行？

| 断点位置 | 展开查看 | 应该回答的问题 |
|---|---|---|
| `demo()` 的 `model.invoke()` 之前 | `OLD_MANUAL`、`report`、消息列表 | 模型实际收到哪些信息？控制台文字也发出去了吗？ |
| `proposal = text_of(ai).strip()` 处 | `type(ai)`、`ai.content`、`ai.tool_calls` | 返回的是一条回复，还是完整历史？是写规则还是请求执行？ |
| `valid_patch()` 内 | `parts`、`number`、`instruction` | 文本怎样分割？为什么通过或拒绝？ |
| `run_tasks()` 的两个工具函数内 | `actions`、`notes` | 工具是否真的执行？调用顺序是什么？ |
| `ok = ...` 处 | `actions`、`notes`、`task` | 是根据真实记录验收，还是只相信模型的话？ |
| 比较 `before`、`after` 处 | 两次成绩和 `active_manual` | 格式通过是否已经等于采用？为什么同分不算提升？ |

在 `mini.py` 中，沿着 `_invoke()` → `_run_tools()` → 下一次 `_invoke()` 看工具循环。先用“单步跳过”观察本项目变量，不必一开始进入 SDK 内部每一层实现。

继续执行或重启在线脚本可能再次调用 API；在调试器中反复求值 `invoke()` 或工具函数也会产生真实调用。只查看变量，和重新执行函数，是两件事。

## 2. `invoke()` 返回什么？为什么没有输入和历史？

对这里的普通聊天模型调用：

```python
messages = [SystemMessage(content="你是助手。"), HumanMessage(content="你好")]
ai = model.invoke(messages)
```

`messages` 是输入列表，`ai` 是本次新生成的 `AIMessage`。输入不出现在返回对象中，不代表模型没有收到它。`AIMessage` 不是整个聊天记录。

如果继续对话，需要程序或框架组织历史，例如：

```python
messages.append(ai)
messages.append(HumanMessage(content="请继续解释"))
ai2 = model.invoke(messages)
```

单独使用 `model.invoke([新问题])` 不会自动继承前一次消息。`Runner` 则在一次运行中追加用户消息、模型回复和工具结果，再选择窗口发送；跨轮继续时还需要提供相应历史。

对象不同，返回结构也可能不同：聊天模型返回 `AIMessage`；本项目 `Runner.run()` 返回 `Turn`；`7_1` 中执行 Agent 的返回值含 `messages`。不要把所有 `.invoke()` 的返回值当成同一种结构。

调试时优先看：

- `content`：本次回复正文。
- `tool_calls`：结构化工具请求；正文里出现工具名不代表请求调用。
- `usage_metadata`：用量，不是对话历史；输出 token 统计也可能包含推理 token。
- `response_metadata`：提供方报告的模型、结束原因等信息。兼容接口中的提供方标签不一定等于实际模型厂商，要结合配置看。

## 3. 工具注释很清楚，为什么没有调用？

先检查三个环节：是否提供工具定义？当前任务是否需要工具？是否有程序执行请求？

```python
model = live_model()
bound = model.bind_tools([read_progress, write_note])

# 普通调用，不会因为前一行就自动带上工具。
ai = model.invoke(messages)

# 这个调用对象携带工具定义，但返回的仍然只是回复或工具请求。
ai = bound.invoke(messages)
```

`bind_tools()` 返回绑定后的调用对象，不会让所有后续基础 `model.invoke()` 自动绑定。`@tool` 的说明只有通过工具定义提供给模型后，才能帮助选择工具。

`run_tasks(model, ...)` 接收的是 `demo()` 中同一个基础模型对象，不是自动复制一个模型。`Runner` 内部使用 `model.bind_tools(tools)` 得到的对象发请求，再由 `_run_tools()` 执行本地函数。

`hs_14` 中直接调用模型的任务是“写操作规则”，所以返回规则文本；`run_tasks()` 的任务才是“实际读取进度、写入笔记”。两次请求的职责不同。

Tool Calling 表达工具名和参数；ReAct 强调根据行动结果继续决策。它们可以组合使用，不是二选一，也不要求公开模型内部推理过程。

## 4. “手册”、Skill、目录、历史分别是什么？

| 名称 | 本项目里的含义 | 不要混淆成 |
|---|---|---|
| `hs_14` 的手册 | `OLD_MANUAL` 或 `candidate_manual` 这段操作提示文字 | 特殊框架对象、已训练的模型知识 |
| `hs_13` 的 `MAP` | 资料名称、路径和读取指引 | 用户当前问题、历史摘要 |
| `hs_13` 的 `full` | 目录加全部模拟文档正文，只用于长度比较 | 全部历史对话、实际发给模型的输入 |
| 历史记录 | 用户消息、模型回复和工具结果 | 技能说明或架构文档 |
| Skill | 可按需加载的任务指引和配套资源 | 单个 `@tool` 函数 |

Skill 可以跨多个文件，内部先给分支目录，再按需读取方法、模板或参考文档。这个机制与 `hs_13` 的“目录 → 正文”一致。

`7_1_skill_registry_demo.py` 展示得更完整：扫描技能、提取简介、模型选技能、注入正文，再读取资源或执行脚本。扫描时程序已读取正文到内存，不代表正文已发给模型。`hs_13` 则只用字典模拟资料，而且用户已经指定要打开哪个路径，没有展示自主选技能。

历史总结解决的是“已发生的对话怎样压缩”；渐进披露解决的是“外部资料什么时候加载”；`hs_10` 解决的是“怎样修改规则条目而保留其余规则”。三者可以组合，但不是同一段实现。历史总结可回看 [4_1_message_history_demo.py](../4_1_message_history_demo.py) 的 Demo 4。

Skill 的发现、选择、加载涉及上下文管理，配套脚本的执行涉及工具管理和权限。不能只把 Skill 归成工具执行部分。

## 5. 多次被拒绝，是模型差还是规则太严？

先定位拒绝发生在哪一关，再评价原因：

1. 目标是否允许修改？只读拒绝不代表行为测试太严格。
2. 提案格式是否正确？格式通过不代表内容有效。
3. 测试是否通过？具体哪个输入失败、期望什么、实际什么？
4. 模型是否收到当前代码、要求和失败原因？`print()` 的控制台内容不会自动发送给模型。
5. 是否有可用的修正入口和明确反馈？只返回一个错误码，模型可能只能猜。
6. 是否被上下文裁剪、步数上限或调用异常中断？这些不能直接归因于推理能力。

“保护机制有效”和“AI 完成任务”应分别检查。测试不可改，说明保护有效；业务代码仍算错，说明任务未完成。进程退出码为 0、控制台的“正例”标签，也不保证业务任务成功。

`hs_11` 用运费函数演示：改测试被拒绝，全部免运费被测试拒绝，修正 `>` 为 `>=` 才通过。固定提案是人为准备的教学用例；真实模型部分重新开始，不能混为模型自行完成的行为。

`hs_14` 的 `0/2` 是“通过 0 个，共 2 个任务”，不是模型能力的总分。当前版本检查真实工具顺序和写入内容，没有强弱执行器开关。旧、新手册用相同模型配置和任务比较，但一次两题结果仍可能波动。

## 6. Python 不熟时，先做这些小实验

### 分割和解包：与 JavaScript 有一点不同

```python
parts = "2|先读进度|再写笔记".split("|", 1)
# ['2', '先读进度|再写笔记']：最多切一次，剩余文字保留。
number, instruction = parts
# 相当于 number = parts[0]; instruction = parts[1]

bool(instruction.strip())  # 去掉首尾空白，判断是否还有内容。
bool("   ".strip())       # False
```

Python 的解包类似 JS 的 `const [number, instruction] = parts`。普通解包要求元素数匹配：

```python
"a|b|c|d".split("|", 3)  # ['a', 'b', 'c', 'd']，切三次得到四项。
# a, b, c = 上面的列表  → ValueError，四项无法分给三个变量。
a, b, c = "a|b|c|d".split("|", 2)  # c 是 'c|d'
a, b, *rest = "a|b|c|d".split("|")  # rest 是 ['c', 'd']
```

JS 的 `"a|b|c|d".split("|", 2)` 是最多返回两项 `['a', 'b']`，后面的内容不返回。Python 第二个参数是最多分割次数，不能直接照搬 JS 参数含义。

### `--offline` 是怎样生效的？

`hs_11` 的 `ArgumentParser` 创建命令行解析器；`add_argument("--offline", action="store_true")` 定义开关；`parse_args()` 读取启动参数。写了 `--offline` 时 `args.offline` 是 `True`，否则是 `False`。

解析器只识别参数，真正跳过模型调用的是 `demo(offline=args.offline)` 内的条件分支。`description=__doc__` 使用文件开头的文档字符串作为帮助说明，可用 `--help` 查看。

### AST：代码也可以先被解析成结构

`hs_11` 用 Python 的 `ast` 模块检查候选代码，不必一开始掌握全部节点类型。

```python
tree = ast.parse(source)  # 解析，不执行 source。
fn = tree.body[0]        # 最外层第一条语句的结构对象，不是第一行文字。
nodes = list(ast.walk(tree))  # 所有层次的节点，包括函数内部。
```

`sum(isinstance(node, ast.FunctionDef) for node in nodes)` 数出函数定义数量：`True` 求和时按 1、`False` 按 0。只看最外层可能漏掉函数内部嵌套的函数，所以还要检查总数。

`ast.Name` 表示名字，`node.id` 是名字文本；`ast.Constant` 表示常量，`node.value` 是实际值。示例只允许变量 `amount`，常量只允许指定范围的整数和小数。这些是本例的限制，不是普通 Python 函数的限制。

`type(value) not in (int, float) or not 0 <= value <= 1_000_000` 表示“类型不对，或者数值超范围”。左边已为真时 `or` 不再计算右边，所以不会拿字符串与数字比较；`1_000_000` 就是便于阅读的 `1000000`。这里用精确类型检查还会排除布尔值。

## 7. 将问题整理成可验证的学习笔记

每次向 AI 提问后，记录下面五项，而不是只复制一大段解释：

```text
现象：这次 model.invoke() 的返回值没有输入消息，也没有 tool_calls。
原先理解：模型会自动返回并记住全部历史，看到工具名就调用。
代码证据：这次是未绑定工具的基础模型调用，任务是写规则。
修正理解：返回的是本次 AIMessage；历史由程序组织；执行要经过工具循环。
验证方法：分别查看 messages、ai.content、ai.tool_calls 和工具内的断点。
```

如果解释与运行结果冲突，请让 AI 对照当前文件重新核实。还要问清“如果删掉这个检查，会发生什么”，用反例确认你理解的是机制，而不只是记住了术语。
